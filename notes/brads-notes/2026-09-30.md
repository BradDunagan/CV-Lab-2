# A gap sweep: the Cube lowered onto the Table, measured down to contact

The visual-servoing write-up ("cv-lab and Visual Servoing", a Claude Doc)
proposed a gap sweep for the assembly case: two parts in one image, one closing
on the other. This entry records what was built and what it measured. The
proposal and the build differ in a few places, and each difference is noted
where it comes up.

## The answer, first

**With the scene's own overhead lamp, no gap is measured at any step.** The
cube's shadow falls exactly on the stretch of table edge under it. Both facing
edges lose their contrast there and neither is detected. With one area light
added on the camera side (`scenes/gap-1-front.json`), the curve is:

| gap (mm) | true (px) | measured (px) | error (px) | error (mm) | spans both | why no pair |
|---|---|---|---|---|---|---|
| 50 | 59.740 | 59.436 | −0.304 | −0.262 | 0 | |
| 20 | 23.480 | 23.077 | −0.403 | −0.346 | 0 | |
| 10 | 11.672 | 11.511 | −0.161 | −0.138 | 0 | |
| 5 | 5.819 | 5.840 | +0.021 | +0.018 | 0 | |
| 2 | 2.324 | 3.514 | **+1.190** | **+1.022** | 0 | |
| 1 | 1.161 | — | — | — | 1 | detected edges are not parallel |
| 0.5 | 0.580 | — | — | — | 2 | no detection matched Cube's edge |
| 0 | 0.000 | — | — | — | 0 | no detection matched Cube's edge |

512 px, 96 samples, no denoise, 1.164 px per mm of gap at this distance.

- **From 50 down to 5 mm:** the error stays within 0.4 px (0.35 mm).
- **At 2 mm:** both edges are still found as two separate lines, but they read 1.2 px too far apart.
- **From 1 mm down:** the cube's bottom edge breaks into pieces, and some pieces run onto the table edge.
- **At contact:** there is one image edge where the scene has two mesh edges, which is the T-junction problem in another form.

## What was built

The proposal survived as three stages: generate, `lab`, analyse. These parts
are new:

- **`npm run generate -- --shots <file>`.** It renders a JSON list of shots
  instead of the scene's own plan. A shot can carry `transforms`: an object's
  name mapped to a partial position, rotation or scale, merged over where the
  object is. Placements are absolute. The whole list is checked before
  anything renders (`checkShots`), and moving an object the scene does not
  include is refused (`resolveShotObjects`). The driver applies the
  placements just before each render. Its three tests sit with the
  driver's others in `test/groundtruth.js`.
- **`commitObjectChanges()` in pt-lab.** This one was not in the proposal.
  `setObjectTransform` only marks objects dirty. The traced scene is rebuilt
  on the way out of edit mode, and the generator never enters edit mode, so
  a moved cube would have been rendered where it was. Ground truth would
  still have followed it, because it reads the mesh matrices directly. That
  is a silent mismatch between picture and truth. pt-lab's own
  `exportSeries` rebuilds the scene after each move for the same reason.
  The generator page's `transform()` now calls the new method, and the
  Scene Editor's drag path is unchanged.
- **`src/lab/gapsweep.js`.** It is pure and tested by `test/gapsweep.js`:
  12 tests, each with an arithmetic expected value. It finds the facing truth
  pair: one edge belonging only to each part, parallel to within 5°,
  overlapping by at least 10 px, and within the gap plus 2 cm of each other
  **in depth**. The depth test keeps the table's back edge from being taken
  for its front edge when it projects close. Among the pairs that pass, the
  one closest in the image wins. The gap is signed toward the moving part
  and measured at the middle of the overlap. Detections are measured at the
  same point.
- **`scripts/gap-sweep.js`.** It runs plain node and calls the two Electron
  CLIs as child processes. Defaults are `saved:gap-1`, Cube onto Table,
  `--axis 0,1,0` and gaps of 50, 20, 10, 5, 2, 1, 0.5 and 0 mm. It writes
  `shots.json` into the generated directory, so `--skip-render` can refuse
  renders that belong to different shots.
- **`scenes/gap-1.json`.** The Cube sits at (−0.3, 0.8, 0.45) with no
  rotation. Its front face is at z = 0.5, flush with the table's front edge
  (the table top spans z −0.5…0.5 with its surface at y = 0.75), so the
  cube's bottom-front edge and the table's top-front edge close onto each
  other. The camera is 0.45 m from (−0.3, 0.76, 0.5) at 20° yaw and 15°
  elevation, held fixed.

The proposal called for a 6-DoF relative-pose error. The build measures the
**image** gap instead. There is no pose estimator here, and adding one would
put its errors into the result. The image gap is also the quantity
image-based servoing drives to zero.

## Dead ends, with numbers

**My first version extrapolated, and that made a result look good.** For each
truth edge it took the longest matched detection. At 20 mm that was a 21 px
fragment of the cube edge (x 201–222) and a table piece starting at x 316. The
measuring point was x ≈ 258, and extending both lines read an error of
+1.14 px. At 50 mm the same extrapolation happened to land within 0.11 px, on
a frame where the table edge under the cube was **never detected**. The
overlay showed it: a white, unmatched truth edge running through the shadow.
The fix uses, for each truth edge, the matched piece that covers the measuring
point. A row with no such piece gets no error and a `reason`, such as
"detections stop 57.1 px short of the measuring point". Two tests pin this
behaviour.

**Under the overhead lamp**, after that fix:

```
50  59.740  "detections stop 57.1 px short of the measuring point"
20  23.480  "detections stop 60.5 px short of the measuring point"
10 … 0      "no detection matched Cube's edge"
```

Both facing edges are present in the truth and absent from the detections.
The front faces of the cube and the table are near black under a lamp
directly overhead, and the strip of table top between them is in the cube's
shadow. The prediction was that the held part's shadow would add false edges
near contact. Here it removed the real ones. That is worse, and a real cell
with overhead lighting would have the same problem.

## Not settled

- **Why 2 mm reads 1.2 px wide.** It is probably blur: at `sigma=1.4`, the two
  gradient peaks of a 2.3 px strip are pushed outward. The check is a sweep
  over `sigma` at the 2 mm and 5 mm renders, which needs no new renders. Untested.
- **Whether −0.3 to −0.4 px at 20 and 50 mm is bias or noise.** One render
  per step can't tell. Two seeds per step would.
- **The camera-angle grid** from the proposal. One angle so far.
- **Peg and hole.** Each library key appears once per scene, so a pair of
  imported parts is the next fixture.

## Rerunning

```bash
npm run build:generate        # pt-lab changed: commitObjectChanges
npm run gap-sweep -- --name gap-1                                   # overhead lamp only
npm run gap-sweep -- --name gap-1-front --scene saved:gap-1-front   # + front area light
```

Each takes about 2 m 50 s: 8 renders at about 21 s each, then the lab and the
overlays. This shell's default `node` is 18.17; the build needs 22, which is
under nvm.
