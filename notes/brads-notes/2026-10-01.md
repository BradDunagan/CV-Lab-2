# 2026-10-01

# The gap sweep's numbers moved, and the lab was not why

A small formatting change to the gap sweep's CSV was checked by re-running the
front-lit analysis with `--skip-render`. The numbers came out different from
the ones in [2026-09-30](2026-09-30.md):

| | 09-30 | today |
|---|---|---|
| 50 mm error | −0.304 px | −0.317 px |
| shading detections in the gap at 50 mm | 6 | 10 |
| 1 mm | no pair ("detected edges are not parallel") | pair found, +2.395 px |

The overlays showed the detected segments themselves had changed, not just the
analysis of them. Reproducibility is one of this project's two requirements,
so this was chased before anything else.

## The answer, first

**The renders had been replaced.** The front-lit sweep was run a second time
under the same `--name`, about 1.5 hours after the run whose numbers were
reported:

| file | written |
|---|---|
| the run log behind the 09-30 numbers | 09-30 17:22:54 |
| `generated/gap-1-front/shots.json` | 09-30 18:50:50 |
| the eight renders and their truth | 09-30 18:51–18:53 |

A gap-sweep run writes `shots.json` first and then renders, which matches
these times. Path tracing is not byte-reproducible: the lamp commit measured
two renders of one scene differing by 3.4–4.8 levels per pixel. Today's
`--skip-render` analysed a second sample of the same shots, and nothing in the
tooling said so.

## Ruled out on the way, with how

- **Inputs changed after they were written.** No file in the run was modified after the run that wrote it.
- **Code.** Nothing that produces detections changed between the runs; the only new file, `src/lab/gapsweep.js`, reads the output.
- **The addon.** There is one `cvlab.node`, built 09-20.
- **The display's colour profile reaching decoding.** `load` already passes `colorSpaceConversion: 'none'`.
- **The lab being nondeterministic.** The 50 mm image went through the lab three times with byte-identical `features.json`. All eight images were then run again, immediately after a GPU warm-up render of the same scene, and compared step by step with the session logs' output hashes: **all 19 steps of all 8 images identical.** The GPU guess was wrong.

**A mistake of mine worth recording:** I first said the renders were untouched
since they were written. I had compared the files' times with each other,
which only shows that they were all written together. The time that settled it
was the run log's. The question to ask is when the file was written relative
to the run that used it.

## What the accident measured

Two independent renders of the same shots, through the same lab, are a
direct measure of render noise. That settles one of 09-30's open questions:

| gap | run 1 error (px) | run 2 error (px) | run 1 spans both | run 2 spans both |
|---|---|---|---|---|
| 50 mm | −0.304 | −0.317 | 0 | 0 |
| 20 mm | −0.403 | −0.371 | 0 | 0 |
| 10 mm | −0.161 | −0.168 | 0 | 0 |
| 5 mm | +0.021 | +0.016 | 0 | 0 |
| 2 mm | +1.190 | +1.206 | 0 | 0 |
| 1 mm | no pair | +2.395 | 1 | 1 |
| 0.5 mm | no pair | no pair | 2 | 1 |
| 0 mm | no pair | no pair | 0 | 0 |

- **20–50 mm:** the −0.3 to −0.4 px error repeats to within 0.03 px, so it is a
  bias, not noise.
- **2 mm:** the +1.2 px overestimate repeats to within 0.02 px.
- **1 mm:** whether there is a pair at all depends on the noise in that render.
  The answer there is "unstable", and a single run reporting either outcome is
  misleading.

Two samples is the minimum. The run-to-run spread at 1 mm needs more.

## What changed because of it

- **A run name is rendered once** (`7838868`). Rendering into a name whose
  `shots.json` exists is refused, saying when it was rendered. The three
  options are a new `--name`, `--skip-render`, or `--overwrite`.
- **Every analysis records what it measured** (`f729aea`). `gap-sweep.json`
  carries a SHA-256 of each shot's render, truth and three passes. A
  `--skip-render` over different files names the changed shots and keeps the
  previous record as `gap-sweep.replaced-<time>.json`.

  The first guard stops this happening through `gap-sweep`; the second catches
  it however it happens, for example `npm run generate` writing into the
  directory by hand.

The 09-30 records of `gap-1` and `gap-1-front` predate the hashes. They were
kept as `replaced-` files, with a note that they cannot be checked.

## Not settled

- **Whether the 20–50 mm bias belongs to the detector, the truth, or the
  measuring point.** The 09-30 sigma question applies here too, and the same
  sigma sweep over existing renders would answer both.
- **How unstable 1 mm is.** That needs several samples per gap: a
  `gap-1-front-s2`, `-s3`, and so on, now that names cannot collide.
- **A general version of the guard.** `npm run lab`'s session logs already hash
  every buffer they produce, including each `load`'s decoded image. Comparing
  two runs' `load` hashes would have shown the renders had changed at once.
  What lost that here was `--skip-render` writing its logs over the previous
  ones. Keeping or comparing them, as `gap-sweep.json` now does for its own
  record, is the general fix. It is not done.

# Later: the sigma test. Blur explains the small gaps and not the large ones

The 09-30 note guessed that the 2 mm overestimate was blur: at `sigma=1.4`, the
two gradient peaks of a 2.3 px strip are pushed outward. Earlier today, the
20–50 mm bias was left open as possibly the same thing. Both are questions
about the pipeline, answerable over the existing front-lit renders.
`gap-sweep` gained `--script` for this ("gap-sweep: --script runs another
pipeline over the same renders, into its own results").

There were four copies of `explained.lab`, differing only in
`gaussian(G, sigma=…)`, in `results/sigma-scripts/`, which is ignored. Each was
run with `npm run gap-sweep -- --name gap-1-front --scene saved:gap-1-front
--skip-render --script results/sigma-scripts/sigma-<σ>.lab`. The `sigma-1.4`
copy is byte-identical to `explained.lab` and served as the control: all eight
`features.json` matched the default run byte for byte.

## The answer, first

Error in px, measured − true, over the same eight renders:

| gap (true px) | σ=0.7 | σ=1.0 | σ=1.4 | σ=2.0 |
|---|---|---|---|---|
| 50 mm (59.7) | −0.350 | −0.316 | −0.317 | −0.315 |
| 20 mm (23.5) | −0.393 | −0.360 | −0.371 | −0.353 |
| 10 mm (11.7) | −0.255 | −0.238 | −0.168 | −0.035 |
| 5 mm (5.8) | −0.122 | −0.074 | +0.016 | +0.271 |
| 2 mm (2.3) | +0.234 | +0.470 | +1.206 | +2.242 |
| 1 mm (1.2) | cube edge lost | +1.773 | +2.395 | cube edge lost |
| 0.5 mm, 0 mm | lost | lost | lost | lost |

| | σ=0.7 | σ=1.0 | σ=1.4 | σ=2.0 |
|---|---|---|---|---|
| segments, 50 mm / 2 mm | 226 / 171 | 193 / 195 | 135 / 141 | 86 / 90 |
| shading detections in the gap, 50 mm | 21 | 15 | 10 | 5 |

- **The small-gap overestimate is blur.** At 2 mm it grows almost tenfold
  from σ=0.7 to σ=2.0. At σ=2.0 it already shows at 5 mm, a gap of about 2.9σ.
  The 2 mm overlays show it directly: at σ=0.7 the two detected lines sit on
  their truth edges, and at σ=2.0 the cube's sits above its edge and the
  table's below.
- **The 20–50 mm bias is not blur.** It holds at −0.32 to −0.39 px across a
  threefold range of σ. A shift applied to the whole image would cancel in a
  gap, so this is something that moves one or both edges individually. Two
  untested guesses: a silhouette (the cube's bottom edge) and a crease (the
  table's top edge) placing their gradient peaks differently relative to the
  true geometric edge, or the antialiased boundary of a dark face against a
  lit one.
- **No σ resolves 1 mm.** At σ=0.7 noise breaks the cube's edge up; at
  σ=2.0 blur merges it into the table's. σ=1.0 finds a pair 1.8 px off a 1.2 px
  gap.
- **Small σ costs noise.** σ=0.7 has 2.6× the segments of σ=2.0 at 50 mm,
  and 4× the shading fragments in the gap. `corners` is quadratic in
  segment count.

For gaps of 2–5 mm at this scale (1.16 px per mm), σ≈0.7–1.0 cuts the error
2.5–5× compared with the default. Whether that is worth the noise depends on
what consumes the edges. Nothing here suggests changing the default yet. It
was chosen for whole images, not for two edges a few pixels apart.

## Not settled

- **The 20–50 mm bias.** Split the error per edge: compare each detected
  edge with its own truth edge, not only the gap between them. That needs
  no new renders.
- **σ chosen for the gap only.** A pipeline could blur less only where two
  edges are close. That is a design question, not a measurement.
- **One render set.** These numbers are from the second front-lit render
  set only. The first was overwritten (see above).

# Later still: split per edge, the bias was half a pixel of convention

The sigma test left the 20–50 mm gap bias unexplained. The next step was to
split the gap error into its two edges: where each detected edge crosses the
truth pair's normal at the measuring point, against where its own truth edge
does, with positive toward the cube. ("gap-sweep: the gap error split by edge
-- and it found a half-pixel convention mismatch".)

## The answer, first

At 50 mm, σ = 1.4, the cube edge was +0.295 px and the table edge +0.612.
**Both edges were displaced the same way by about half a pixel.** No property
of one edge does that; a coordinate convention does:

- **The lab's detections** are fitted through pixel indices
  (`native/addon_kernels.c`), so pixel *i*'s centre is at *i*.
- **pt-lab's ground truth** projects the frame onto [0, size] (`toImage`), so
  it puts that centre at *i* + 0.5.

That predicts (−0.5, −0.5) for every detection, which is +0.447 px along these
edges' normal. The two edges' mean was +0.454.

Not taken on one fixture. A single translation least-squares fitted to every
matched segment, over all orientations:

| set | hits | fitted shift (x, y) | rms offset, before → after removing it |
|---|---|---|---|
| `cube1` | 41 | (−0.507, −0.457) | 0.502 → 0.070 px |
| `clutter` | 80 | (−0.448, −0.362) | 0.570 → 0.395 |
| `gap-1-front` | 135 | (−0.384, −0.526) | 0.702 → 0.502 |
| `helmet-512` | 1309 | (−0.167, −0.331) | 1.084 → 1.052 |

## The fix, and what re-measuring every result set showed

The truth moves by −0.5 where it enters the lab (`groundTruth` v2), and the
files keep pt-lab's convention. Both overlays now draw lab coordinates at
(*v* + 0.5)·scale; before, they drew detections half a source pixel up and
left of what they were fitted to. `explain`'s optical centre had the same half
pixel (`explain` v3), which changed 1 cause in 983. ("ground truth enters the
lab in the lab's pixel convention -- every match was half a pixel off".)

Every existing result set was re-run with its own script and flags. The
detections were byte-identical before and after in all seven sets:

| set | segment-hit median | corner-hit median | fitted shift after |
|---|---|---|---|
| `cube1` | 0.527 → **0.062** px | 0.681 → 0.124 | (−0.007, +0.043) |
| `cube` | 0.482 → 0.102 | 0.725 → 0.224 | (+0.029, +0.088) |
| `clutter` | 0.482 → 0.106 | 0.722 → 0.179 | (+0.023, +0.107) |
| `gap-1-front` | 0.445 → 0.187 | 0.827 → 0.438 | (+0.039, −0.094) |
| `helmet-512` | 0.531 → 0.428 | 1.584 → 1.594 | (−0.006, −0.195) |

On the clean cube the detector places edges to about 0.06 px. The helmet
barely moves: its limit is loose matching against a dense mesh. A few edges
near the 3 px tolerance now match; segment misses go from 84 to 79 on `cube`
and from 83 to 76 on `clutter`.

**My claim that the shift "cancels exactly in any gap" was wrong.** It
cancels to within 0.02 px. The 50 mm error moved from −0.317 to −0.338 px,
20 mm by 0.011, and 2 mm by under 0.001. The two edges are not quite parallel
in perspective, so moving the truth slides the measuring point along edges
whose separation varies. The per-edge commit's message says "exactly". That
message is history, and this is the correction.

## What the bias is, now

The per-edge offsets with the convention removed (front-lit, σ = 1.4), with
positive toward the cube:

| gap | cube edge | table edge | gap error |
|---|---|---|---|
| 50 mm | −0.173 | +0.165 | −0.338 |
| 20 mm | −0.230 | +0.151 | −0.382 |
| 10 mm | +0.008 | +0.180 | −0.172 |
| 5 mm | +0.212 | +0.198 | +0.014 |
| 2 mm | +1.083 | −0.123 | +1.206 |

- **At 20–50 mm, each edge is pulled about 0.15–0.23 px toward the
  other.** That is the bias. It is not blur (09-30's σ sweep) and not the
  convention. Still open; antialiasing of a dark face against a lit one, and
  shading gradients near each edge, are the guesses.
- **At 2 mm, the blur's push-apart falls almost entirely on the cube's
  edge,** +1.08 px against −0.12.
- **The table edge sits about +0.15–0.2 px toward the cube at every gap
  of 5 mm and above.** Something about that edge itself, independent of the
  cube.

## Worth keeping from this

- **Every overlay ever made showed the detections slightly off their
  edges.** It read as detector imprecision, because that is what one
  expects to see. The overlay is only as honest as its own coordinate
  mapping.
- **A tolerance hides a constant offset completely.** At 3 px, `match`
  could not see 0.7 px in every comparison.
- **The split was what found it.** A per-edge measurement exposes what a
  difference cancels. Gaps were the wrong place to look for it, and the
  right place to find it.

# Last: two linear renders of the same sweep. The cube edge's offset is real

What happened between the previous section and this one is written up in
`design-lab-model.md` §5, "A fourth: the renderer's tone curve moved the
edges". pt-lab's beauty renders are ACES-tone-mapped, which moved the table
edge about +0.2 px. `generate --tone-mapping linear` now exists, `gap-sweep`
defaults to it (exposure 0.5), and so does the Generate pane's new `tone` row.
Under linear, the table edge sits on its truth. The cube edge kept an offset of
about −0.2 to −0.3 px at 20–50 mm, pushed toward its darker side, which the
design doc leaves open.

One linear run cannot say whether that is a bias or one render's noise. So a
second, independent render of the same shots:

```bash
npm run gap-sweep -- --name gap-1-front-linear-2 --scene saved:gap-1-front
```

Both runs are linear at exposure 0.5, as recorded by the renders themselves,
with σ = 1.4. Per-edge offsets are positive toward the cube:

| gap | error, run 1 → run 2 | cube edge, run 1 → run 2 | table edge, run 1 → run 2 |
|---|---|---|---|
| 50 mm | −0.281 → −0.226 | −0.286 → −0.225 | −0.004 → +0.001 |
| 20 mm | −0.225 → −0.234 | −0.210 → −0.227 | +0.015 → +0.007 |
| 10 mm | −0.034 → −0.037 | −0.039 → −0.034 | −0.005 → +0.003 |
| 5 mm | +0.103 → +0.098 | +0.115 → +0.080 | +0.013 → −0.018 |
| 2 mm | +1.179 → +1.224 | +1.137 → +1.178 | −0.042 → −0.046 |
| 1, 0.5, 0 mm | no pair in either: no detection matched the cube's edge | | |

- **The cube edge's offset is a bias, not noise.** It is −0.23 to −0.29 px
  at 50 mm and −0.21 to −0.23 at 20 mm, with the two renders agreeing to
  within 0.06 px. It is stable enough to chase directly. A render with the
  front light moved, or with the cube a different colour, should say whether
  it follows the lighting or the edge.
- **The table edge stays fixed,** within ±0.02 px in both.
- **The 2 mm blur push-apart repeats,** at +1.18 and +1.22 px.
- **At 1 mm neither linear run found the cube's edge.** The ACES runs
  sometimes did (+2.40 px at σ = 1.4 on 09-30's front-lit set). Untested
  guess: under linear at this exposure, the cube edge's contrast against the
  shadowed gap is lower than under the curve, which lifts dark tones.

# Very last: three one-change scenes. "Toward the darker side" was wrong

The section above suggested moving the light or changing the cube's colour, to
see whether the cube edge's offset follows its brightness or its geometry.
Three scenes, each one change from `gap-1-front`, each its own linear sweep
(exposure 0.5, σ = 1.4). Cube edge offsets are positive toward the cube, and
brightness is shown as gap side | cube face, measured in the render:

| scene | 50 mm | 20 mm | 10 mm | 5 mm |
|---|---|---|---|---|
| `gap-1-front`, run 2 | −0.225 (0.17 \| 0.37) | −0.227 (0.08 \| 0.32) | −0.034 | +0.080 |
| `-low`: light y 1.0 → 0.8 | −0.112 (0.14 \| 0.47) | −0.180 (0.06 \| 0.42) | −0.132 | −0.116 |
| `-dark`: cube #b01818 → #1a1a1a | not found | +0.200 (0.07 \| 0.14) | +0.490 | +1.046 |
| `-dark-matte`: and shininess 0.6 → 0 | **−0.005** (0.17 \| 0.05) | too faint | — | — |

**Two predictions of mine failed before the test worked.**

- **Lowering the light** was meant to brighten the gap strip. It darkened
  it, and the cube face got brighter.
- **The dark cube** was meant to render darker than the gap. Its gloss
  reflected the front light, and it stayed slightly brighter, except at 5 mm,
  where they are about equal.

Only the matte dark cube reversed the contrast. Chosen by reasoning about
albedo, two of the three missed. The renders had to be measured.

**What it showed anyway:**

- **The rule breaks twice.** The dark glossy cube had the same darker side
  as the red one, and its offset flipped sign. The matte cube, with its
  darker side finally reversed, put the edge on its truth at 50 mm: −0.005 px
  detected, −0.021 in the render.
- **The table edge never moved** from within ±0.02 px.
- **A glossy face is common to every offset seen.** But `cube1`'s cube is
  glossy too, at the same 0.6, and was clean (0.03 px RMS), so gloss alone
  does not explain it. Something about the front light and gloss together,
  perhaps.

**Next:** a matte RED cube, the original brightness relationship without the
gloss. The design doc's paragraph is corrected (§5, "A fourth"), and so is
CLAUDE.md's open question. The scene files are committed.

**Not gloss.** The offset survives without it, and that fits `cube1` being
glossy and clean. Across the five scenes it tracks the cube face against the
gap: face brighter, the edge sits 0.1–0.3 px toward the gap; face darker
(matte dark), it sits on its truth. The dark glossy cube's +0.20 fits nothing.

**Stopped here, on purpose, with the cause unexplained.** Brad asked how many
variations to try before moving on. The answer given: one more, because it
was a yes/no question (is it gloss?), and then stop. Any variant after it
would refine an explanation for ~0.3 px in a synthetic image, while the
1–2 mm blur push-apart is 1.2–2.4 px, exactly where assembly needs accuracy.
The rule: stop running variants once another one could not change what
happens next. The scenes are committed for whoever reopens it.
