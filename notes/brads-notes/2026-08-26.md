## The cost table was protecting a bug

`fit` scanned the whole image once per segment — O(segments × pixels) — and
took **7.7 s** on a 1024² checkerboard. `design-lab-model.md` §5 said 84 ms.

The interesting part is why it survived: `merge` had the identical loop and was
fixed two commits earlier, in the same session, by someone who then did not
look one file across. The table is what stopped them. **84 ms is roughly what a
correct implementation costs** — it now measures 39 ms — so the number looked
right and nobody re-measured it. A wrong number that looks wrong gets fixed; a
wrong number that looks right protects the bug underneath it.

Both call `cv_label_index` now, so a third consumer of a label map cannot
repeat it.

`corners` is 45× worse than the same table claimed and is **not fixed**:

| | doc said | measured |
|---|---|---|
| 512², 6,110 features | 155 ms | **5.5 s** |
| 1024², 24,510 features | 2.7 s | **125 s** |

Two minutes on a megapixel of checkerboard. Quadratic in segments, and the
clustering pass quadratic again in candidates. This is the wall for step 3, and
the "2.7 s" figure that has been carried into planning is wrong by 45×.

Also: the table never said what parameters produced it, and could not be
reproduced. At the **default** `minPixels=8` that pipeline finds *zero*
segments at every size — `pattern(kind=checker)` draws 8-pixel blocks and no
run of one survives a blur and non-maximum suppression. It was measured at
`minPixels=3`. Recorded now.

## `-ffp-contract=off` was only half of it

The flag was written down as decided in §5 and §9 and never reached
`binding.gyp`. `otool -tv` found **167** `fmadd`/`fmla` in the arm64 build of
`kernels.o`; baseline x86-64 has no FMA and gets neither `-mfma` nor
`-march=x86-64-v3` from node-gyp. Two platforms, two answers, for the life of
the project. Nothing failed, because nothing compared a result on one machine
against a result on another.

Added the flag, added `test/determinism.js`, pushed. **The matrix failed** —
three platforms, three different hashes for `fit`. And **Linux disagreed with
Windows**, same instruction set, same flags, which no compiler flag explains.

libm. IEEE 754 requires `+ - * / sqrt` to be correctly rounded and says nothing
about `atan2`, `sin`, `cos` or `hypot`; glibc, Apple's libm and MSVC's UCRT are
three implementations. `cv_tls_line` was doing
`0.5·atan2(2cxy, cxx−cyy)` then `sin`/`cos` to find the principal axis of a
2×2 — which needs no trigonometry at all. Algebraic form, only `+ − × ÷ √`:

```
d = cxx − cyy    r = √(d² + 4cxy²)    major axis ∥ (d + r, 2cxy)
```

with the `(2cxy, r − d)` form for `d < 0`, where the first cancels
catastrophically. `cv_atan2` and `cv_cos_degrees` are polynomial, checked
against libm over ~2.4M points: worst error 4.4e-16 rad. Accuracy is the
*secondary* property — a function deterministically off by 1e-16 is worth more
here than one optimally accurate and platform-dependent.

**Why it hid in exactly one output.** Every buffer narrows to `f32` on the way
out, about eight orders of margin, so all fourteen pixel hashes matched from
the start. Feature records hash full-precision doubles and absorb nothing. The
divergence was invisible everywhere except where this lab claims *sub-pixel*
accuracy.

Still not guaranteed, written into §5 3b: `gaussian`'s `exp`,
`toLinear`/`toSrgb`'s `pow`, `orient`'s `atan2` all remain and all write `f32`.
Margin, not proof — roughly 1e-9 per value of landing on an `f32` rounding
boundary, so ~1% per 12 MP image.

## Things that were surprising

- **Svelte swallows an `onMount` exception.** A large edit silently did not
  apply — anchored on text an earlier edit in the same script had already
  changed. It compiled; `onMount` died on `onMenuCommand is not defined` with
  **no console error**. The app came up with a working command bar and zero
  frames. Found only because a screenshot driver reported `canvases: 0`
  alongside `slots: [A,B,E,M]`.
- **Electron lower-cases menu roles.** A built template reports `selectall`
  and `toggledevtools`, not the camelCase the docs use for input.
- **`Menu.getApplicationMenu()` said "CV-Lab" while macOS drew "Electron".**
  The menu object was right; the menu bar reads `CFBundleName` from the running
  bundle, before any JavaScript runs. Reading the API back is not looking at
  the screen. Brad caught it; the check hadn't.
- **Replacing the default Electron menu silently removes Cmd+C/V/X/A inside a
  text input**, and Toggle Developer Tools. `Menu.setApplicationMenu` had never
  been called here, so the default was quietly providing both.
- **nvm's `default → lts/*` resolving to an uninstalled version falls back to
  `system`** with no error — `nvm ls` just says `-> system`. That is how a
  shell kept landing on Node 18.17.1 while 22 and 24 sat installed.

## Dead ends

- **paneless `appHeaderItems` for the toolbar.** It is the right API — items
  carry a `selection` that shows a setting's current value. But `.header-items`
  is `position: absolute; left: 0; right: 0; justify-content: center;
  gap: 10%`, which suits the three or four `rr` uses and puts the first of six
  underneath the app title. Went back to a toolbar, then to a native menu.
- **`screencapture` for screenshots.** Needs screen-recording permission and
  hangs without it. `win.webContents.capturePage()` needs no permission and
  captures the window rather than the desktop.
- **Hiding the app title to remove the third copy of the app's name** — cannot
  be done alone. `AppTitle` is the *only* trigger for paneless's app menu; it
  anchors `menuPortalStore.showMenu` to its own rect. Had to wait for the menu
  to be native.

## Step 3, later the same day

The "Next" above was written before step 3 existed; it got built in the same

### The three commands

`--` is not decoration. `npm run` swallows anything before it, so
`npm run generate --out x` silently loses the flag.

```bash
npm run build:generate                                     # once
npm run generate -- --out generated/ --positions 3 --lighting 2
npm run lab -- --script pipeline.lab --out results/ generated/*.png
```

**1. `build:generate`** → `vite build --config vite.generate.config.mjs`.
Compiles `src/generate/` into `dist-generate/`, pulling in pt-lab's source,
three.js, three-gpu-pathtracer and the OIDN denoiser (~1.1 MB plus pt-lab's
`.glb` assets). Only needed again when `src/generate/` or pt-lab changes.

Separate from `build:renderer` on purpose — the app's bundle has no use for a
path tracer, and CI never builds this. `pt-lab` is a Vite **alias**, not a
dependency: a `file:` dep has to resolve at *install* time even when nothing
imports it, so putting it in `package.json` would break `npm ci` anywhere the
sibling checkout is absent.

**2. `generate`** → `electron scripts/generate-cli.js`. Electron because path
tracing is WebGL and needs a GPU context; the window is never shown.

Registers a `gen://` scheme before app-ready. That exists because three.js's
loaders use `fetch()` and **Chromium refuses `fetch()` on `file://`** — the
first attempt died with a bare "Failed to fetch". In-process handler, no TCP
port: `gen://lab/` serves the built page, `gen://lab/assets/` serves pt-lab's
own assets from the sibling checkout, which is where its default URLs already
point.

Then 3 × 2 = 6 images. Positions orbit the camera a full turn (yaw 0.00, 2.09,
4.19) and nudge the look-at target so the subject is not always centred;
lighting doubles environment intensity (0.5, 1.0). Each image goes through
pt-lab's own `exportPNG` — converge, denoise, downscale, **tag as sRGB** — and
arrives as a browser download the CLI intercepts.

Defaults not overridden above: `--size 512`, `--samples 96`. Cost is about
**20 s an image** at 384px/48 samples. `--dry-run` prints the sweep without
rendering, which is worth doing before committing several minutes.

**3. `lab`** → `electron scripts/lab-cli.js`. Also Electron, for a *different*
reason: `load` borrows Chromium's image decoder, and that only exists in a
renderer. Nothing under plain node can open a PNG.

The shell expands `generated/*.png`; bare paths are treated as images. Per
image it resets the session (slot names repeat — a leftover binding would feed
one image's buffer into the next image's pipeline), prepends
`A = load(..., from=srgb, as=srgb)`, runs the script, and writes
`<name>.session.json` and `<name>.features.json`.

Exit codes mean something: 0 all passed, 1 a pipeline failed, 2 a usage error.

### The division of labour is the point

Generating needs a GPU and takes minutes. Running the pipeline needs neither
and took **0.6 s for all six**. So: generate once, then re-run `lab` as often
as you like while tuning `minMag`, `minPixels`, `sigma`.

### First numbers, damaged helmet at 384px

|            | intensity 0.5 | intensity 1.0 |
|---|---|---|
| yaw 0.00   | 432 segments  | 446 |
| yaw 2.09   | 458 segments  | 480 |
| yaw 4.19   | 361 segments  | 375 |

Corners ran 1005–1417.

Two things fall out. **Brighter always gives more segments** — more gradient
clears `minMag` — and it moves the count by 14–22. **Pose moves it much
further**, 361 to 480. So if a sweep is looking for the pipeline's sensitivity,
position is the bigger lever.

A different regime from the cube entirely: 9 segments there, ~450 here,
because a photoreal render fires on texture and not just silhouette. Also
reassuring about the `corners` wall — ~450 segments is instant; the 125 s
figure was at 24,510.
