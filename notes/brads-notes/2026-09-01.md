# 2026-09-01

Shipping the image generator as a feature of the app rather than as something
only a working copy can do. The change itself was straightforward; what it
turned up was not.

Five commits, five CI runs, four of them red. One of the reds was a real
product defect that predated all of this by nine days. Three were mine, and
they rhyme.

## The packaged app had never worked

Not the generator — the **app**. Found by writing a smoke test that launches
the artifact and asking it a question:

```
[page] error Unable to load preload script: …/app.asar/src/preload.js
[page] error Error: Cannot find module '../scripts/png'
[page] EXCEPTION Error: window.lab is missing.
```

`2856ed9` (23 Aug, *Read what a PNG says about its own encoding*) made the
preload `require('../scripts/png')` for `readPngColour`. `scripts/` was never
in `electron-builder.yml`'s `files:`. So the require threw, `contextBridge`
never ran, and every packaged build since came up to a renderer with no
`window.lab` at all — no slots, no commands, nothing. Forty-one commits.

**Nothing caught it, and everything was green.** `verify:package` asserted the
addon was unpacked, the renderer was inside the archive, the installers
existed. All true. All useless, because **layout is not behaviour**. Three
platforms × every release, reporting success over an app that could not start.

The pattern is the one already in CLAUDE.md — *a check that runs in one place
can pass for the wrong reason* — with a new instance: a check that runs on the
right artifact can still ask the wrong question. `smoke:package` launches the
real thing, attaches over the DevTools protocol, and asks whether the preload
survived, whether the operations registered, whether generation reports ready.

Regressed the bug deliberately to prove the test catches it: `verify:package`
still passes the dead artifact, the smoke test fails it. A check I have not
watched fail is a check I do not believe.

## A green build can ship a broken feature

`src/generate/main.js` calls pt-lab across a Vite alias, in plain JavaScript.
So a method the bundled pt-lab does not define is not a build error, not a type
error, not a lint error. It is a runtime error, in a window nothing opens until
somebody asks for an image.

pt-lab was one commit behind on the remote — `01596e6`, unpushed. Two of three
jobs went green over installers whose `--truth` and `--aovs` would throw.

**The guard could not be a grep, and that is the interesting part.** Both halves
end up in the same bundled file: main.js's call `lab.groundTruthGeometry(...)`
and pt-lab's definition `groundTruthGeometry(size, opts) {`. Searching for the
name finds the call whether or not the definition is there — so the naive
version passes *precisely* when it matters. A definition is an identifier that
is not a property access. The dot is the whole distinction.

Demonstrated rather than argued, by renaming the two definitions in a real
minified bundle and leaving every call site intact:

```
a naive grep would say : PRESENT (wrongly)
this check says missing: [ 'exportAOVs', 'groundTruthGeometry' ]
```

Runs from `postbuild:generate`, so it fires when you build rather than at
release. Does **not** fire under `dev:generate` — npm post-hooks skip a watch.

## Three platform assumptions, three round trips

All mine, all in the same six lines of `findExecutable`, all discovered on a
runner.

| | what I assumed | what is true | cost |
|---|---|---|---|
| 1 | the first extensionless executable in `linux-unpacked/` is the app | it is `chrome_crashpad_handler`, which exits at once | one run |
| 2 | electron-builder names the binary after `productName` | `productFilename` (**CV-Lab**) on macOS/Windows, `sanitizedName.toLowerCase()` (**cv-lab-2**) on Linux | one run |
| 3 | a test fixture can `chmod +x` | NTFS cannot represent a Unix execute bit; Node's chmod is ~a no-op | one run |

Each failure taught the same lesson and I only half-learned it each time.

**#1** reported *"the app never opened a window"* — true, useless, and blaming
the app for a defect in the test. `stdio` was `'ignore'`, so a failed launch
left no evidence at all.

**#2** came from replacing a guess about shape with a guess about a name. The
fix was to stop guessing: anchor on the directory holding `resources/app.asar`,
exclude the known Electron helpers, derive both plausible names rather than
assume one, and use them only to break ties.

**#3** was the test I wrote to stop guessing about platforms, guessing about a
platform. Green on macOS, green on Linux, red on Windows — the shape of a
portable test that is not.

**What actually improved was the diagnostics.** By #3 the failure was a
one-line diagnosis:

```
linux: expected to launch cv-lab-2, got NONE:{"candidates":[],"searched":["C:\\…\\linux-unpacked"]}
```

No other explanation fits that. Compare #1's sentence with no cause in it.

**The real fix was making it testable at all.** `DIST` takes an override, the
module guards its entry point so requiring it launches nothing, and a test
builds the layout each packager really produces — crashpad handler,
`chrome-sandbox` and a `.so` beside the binary — then asks the real function
what it would launch. Three platforms, one machine, milliseconds:

```
linux   -> linux-unpacked/cv-lab-2
win32   -> win-unpacked/CV-Lab.exe
darwin  -> mac-arm64/CV-Lab.app/Contents/MacOS/CV-Lab
```

**I should have built that harness after the first failure, not the second.**
Two of the three round trips were avoidable and I spent them anyway. The tell
was there at #1: a bug I could not reproduce locally in a file that only runs
on CI. That is the moment to make it runnable, not the moment to patch and
push.

## A skip that reads as a pass

The Windows fix could have been "skip the layouts that need an execute bit",
silently. That would have printed the same `ok` as a run checking three times
as much — which is the failure mode this whole day was about, reintroduced at
the end of fixing it.

So it declares itself:

```
       (only win32 — this filesystem has no execute bit)
  ok   the packaged application is found on every platform layout
```

Verified by stubbing `statSync` to clear the execute bits, which is what
Windows effectively does.

## Smaller things

- **A relative output path is wrong for an app.** The Generate pane defaulted
  to `generated`, resolved against a working directory a launched app never
  chose — `/` on macOS from Finder. A customer's first click would have failed
  on a permission error with nothing to suggest why. The main process nominates
  it now: `~/Pictures/CV-Lab` packaged, `./generated` in a working copy, where
  relative-to-cwd is what a CLI should do.
- **`net.fetch` on `file://` reads inside an `.asar`.** I predicted it would
  not — it is the exact trap documented for `.node` — and tested it rather than
  designing around the prediction. A 3.7 MB glTF comes back byte-identical, so
  the generator needed no `asarUnpack`.
- **Prerequisite messages have two audiences.** "Run: npm run build:generate"
  is not something a customer can act on, and a missing bundle in a shipped app
  is a defect in the release rather than anything they did.
- **CI needed pt-lab as a sibling**, same shape as paneless, minus the token —
  `BradDunagan/pt-lab` is public. Its `npm ci` is separate, because the alias
  compiles pt-lab's source and has to resolve three, three-gpu-pathtracer and
  oidn-web from *its* `node_modules`.

## Where it ended

All three platforms, every substantive check:

```
ok   the bundle defines all 18 pt-lab methods the page calls
ok   …/app.asar carries the image generator (36 files)
ok   the preload exposed window.lab
ok   18 operations registered
ok   image generation reports itself ready
ok   images default to <an absolute path>
The packaged app starts and works on darwin/arm64 · win32/x64 · linux/x64
```

Verified before that, on a real packaged app: generated a cube with ground
truth through its own bridge — 9 of 12 edges and 7 of 8 vertices visible,
matching the working-copy runs exactly.

## Still open

- **`scripts/png.js` is runtime code in a scripts directory**, which is what
  made it easy to drop from the package. Moving it to `src/lab/png.js` would
  make the mistake structurally hard to repeat, at the cost of four import
  sites. Not done; it is a rename, and renames deserve their own commit.
- **`test/groundtruth.js` has drifted.** It now holds the generator's
  build-and-packaging checks alongside the ground-truth ones. The banner says
  so, which is honest and not the same as being right. Probably its own suite.
- **The smoke test stops short of rendering.** It proves everything up to the
  first frame survived packaging; it does not prove a frame comes out, because
  that needs a GPU and twenty seconds and CI runners have neither. So the
  thing that would have caught the stale-pt-lab bug at runtime still does not
  exist — the build-time guard is what covers it, and that is a different
  claim.
- **`dev:generate` escapes the bundle guard**, since npm post-hooks do not run
  for a watch.

# Later the same day — driving the app over CDP

Went to the light theme, then the paneless control columns, and spent most of
the day looking at the running app rather than at the code. Writing down how,
because I kept re-deriving it and because two of its limits cost me real time.

## The setup

`npx electron . --remote-debugging-port=9222`, then
`http://127.0.0.1:9222/json/list` for the targets, then a WebSocket per target.
Node 22 has a global `WebSocket`, so a usable client is about fifteen lines with
no dependencies:

```js
const list = await (await fetch('http://127.0.0.1:9222/json/list')).json();
const t = list.find(x => x.type === 'page' && !x.url.startsWith('devtools://'));
const ws = new WebSocket(t.webSocketDebuggerUrl);
// { id, method: 'Runtime.evaluate', params: { expression, returnByValue: true } }
```

`smoke-package.js` already does this and frames its own WebSocket by hand,
because it predates the global. Worth knowing before adding `ws` for anything.

Four methods covered everything: `Runtime.evaluate`, `Page.captureScreenshot`,
`Input.dispatchMouseEvent`, `Input.insertText`.

## The part that actually mattered

**A dispatched input event goes through hit-testing; `element.click()` does
not.** That is the whole reason the hover-overlay defect surfaced.

The `slot` dropdown at the top of the new controls column was drawn, correct,
enabled — and unclickable. paneless reveals a hidden frame header by laying a
transparent 22px `.transient-header-overlay` across the top of the frame, and
the control was under it. The overlay took every click.

`document.elementFromPoint(x, y)` at the control's own centre returned
`DIV.transient-header-overlay`, which ended it. Nothing else I tried said
anything useful: the metadata was right, the SVG was right, the control
reported `enabled: true`.

A test calling `element.click()` would have passed. So would any check that
asked whether the control exists. The test I ended up writing asserts the
property instead — no control's `y` inside the overlay band — and I regressed
the fix to watch it fail before trusting it. It named both offenders.

## Two limits, both of which wasted an hour

**`Page.captureScreenshot` captures one web contents, not the window.** The
embedded pt-lab render is a `WebContentsView` child; screenshotting the
renderer shows that pane *blank*, which looks exactly like a generator that
never started. I went looking for a bug that was not there. The fix is to
connect to the view's own target — it appears in `/json/list` as
`gen://lab/index.html`, but only while a sweep is running.

`screencapture -R x,y,w,h` would sidestep it and is blocked by macOS screen
recording permission for the terminal. Did not pursue.

**CDP reaches renderers; the main process is `--inspect` on another port.**
Different protocol, similar shape. Needed it because Electron menu
accelerators are handled in main and injected key events do not fire them —
so `Cmd+G` does nothing and you send the IPC yourself:

```js
BrowserWindow.getAllWindows()[0].webContents.send('menu:command', 'generate');
```

## A coordinate trap

Do not capture coordinates and then click them. The frame header is
`headerVisible: false` — hidden until hovered — and revealing it moves
everything below. Measure, move the pointer, measure *again*, then click. I
lost a while blaming the app for that.

Also: the controls SVG has a viewBox and letterboxes, so control metadata
coordinates are not screen coordinates and neither is the group's bounding box,
which spans the closed item list. The reliable anchor turned out to be the
rendered `<text>` element.

## Not recorded as fact

Mid-session the slot frame was wider than it should have been and the scaling
mode had flipped to `actual`, which I could not account for from the code. A
clean restart showed correct defaults. Brad was clicking around the window at
the time, which is almost certainly it — but I never proved that, so it is here
