## Why it was headless, honestly

Two tools, two answers, and only one of them holds up.

`lab-cli.js` — genuine. It reads images and writes JSON; there is nothing to
look at. Its window exists **only** because `load` borrows Chromium's decoder,
which lives in a renderer. It also has to run under xvfb in CI.

`generate-cli.js` — symmetry with the runner, plus not wanting a window
stealing focus for minutes. No technical reason at all: `exportPNG` renders
offscreen at the requested size whether the window is visible or not, and the
generator was already excluded from CI, so the usual argument did not apply
either.

The cost was not the missing window. It was never looking.

## Watching it

`--show` on the CLI, and **Panes → Generate Images… (⌘G)** in the app: a
Generate frame with the parameters, a live progress log, and a "show the render
window" box that makes pt-lab's own window appear, path tracing in front of
you.

The constraint that shapes the frame, and will keep shaping it:

> The frame does **not** host the path tracer.

pt-lab is three.js plus an OIDN WASM blob behind a GPU renderer. Bundling it
into the app costs a few megabytes and costs CI an extra checkout, for
something the interface does not otherwise need — and `file:` dependencies must
resolve at *install* time even when nothing imports them, so it cannot simply
be added to package.json without breaking `npm ci` anywhere the sibling
checkout is absent.

So the main process runs it in its own window and sends progress over IPC. Two
small messages: options in, progress and file paths out. No pixels — renders go
to disk and come back through `load` like any other file.

That boundary is why growing the frame is cheap. Every pt-lab control (camera,
material, room kind, object transforms) is one more field in the frame and one
more key in the options object. Nothing about the boundary changes.

Shared orchestration lives in `src/generate/driver.js` — scheme, window,
download intercept, sweep — with the CLI as a wrapper that prints what the
frame displays. Same reasoning as `lab-cli.js` driving `window.lab` rather than
reaching for `Session`: two ways in is two things to drift.

## Things that bit

- **Backticks inside a template literal, third time this session.** `USAGE` in
  generate-cli.js is a template literal, and I wrote a backticked `--room none`
  into the help text. It fails as `SyntaxError: Invalid left-hand side expression in postfix
  operation` — pointing at a line that looks fine. Same shape as the two in
  test/renderer.js. Anything written *into* a template literal has to use
  quotes.
- **`app.quit()` ignores `process.exitCode`** and always exits 0. Looked like
  the fix for the Windows 0xC0000005 crash on exit; turned three passing tests
  into failures. The actual fix was noticing both crashing cases were *usage*
  paths that had no reason to start Electron at all — parse arguments at module
  scope and exit through `process.exit()` before `whenReady`.
- **`console-message`'s positional `level` is a number where 2 is a WARNING.**
  So `level >= 2` quietly promotes every warning to an error. That is how a
  CSP warning failed a generator run and printed itself as a blank line. The
  event object reports level as a string. `test/renderer.js` still uses the
  strict form deliberately — it is what caught the willReadFrequently warning.

## Ground truth, later the same day

The "Still open" list above says the interesting one is that nothing checks
whether the corners found are the corners that exist. Built it.

### The apparatus

pt-lab gained two public methods. `exportAOVs` writes depth, normal and albedo
for the current camera; `groundTruthGeometry` returns, as plain data, every
mesh edge that is a **silhouette**, a **crease** or a mesh **boundary**,
projected into image space, with the fraction of it that is really visible
measured against the depth pass, plus the vertices they meet at.

Silhouettes have to be in there and cannot be precomputed. `EdgesGeometry`
would have been the obvious shortcut and it only knows creases and boundaries —
a sphere has **no creases whatsoever** at any sensible threshold, and a
perfectly obvious outline. Crease-only truth calls the strongest edge in the
picture an invention. So: build the edge→faces adjacency map yourself, and test
front-facing against back-facing per view.

Keying that map by **position across the whole scene** rather than per mesh
turned out to be right by accident and then on purpose: the floor and the wall
standing on it share the entry their common edge sits at, and the dihedral
comes out as the 90° it actually is. One image edge, belonging to neither mesh
alone.

`applyScene` is public, which solves a thing the 08-26 note listed as open. The
helmet arrives through `modelUrl` and is not in pt-lab's library, so nothing
can address it — but the built-in `Cube`, `Table` and `Ball` are, so
`--scene cube` builds a scene out of them and every object comes back with an
id. Object transforms are reachable now too, if that ever matters.

In cv-lab-2 it is two ordinary operations — `groundTruth` reads the JSON in as
`gt-edge`/`gt-vertex` features, `match` scores against it — so the comparison
lands in the log, content-hashed, like a blur. `lab-cli` grew `--truth <dir>`
and prepends `T = groundTruth(...)` per image, exactly the way it already
prepends the load; §4 still has no variables.

### The first render was degenerate and I did not notice for an hour

`--positions 1` gives yaw 0. The cube is axis-aligned. So the camera looked
straight at one face: two faces visible, six vertices, and the three hidden
back edges projecting **exactly onto** the three visible silhouette edges.

The visibility test reported 22% of a hidden edge as visible. That looked like
a tolerance bug, so I replaced the max local slope with a low quantile —
robust at a step, defensible, and I wrote a paragraph explaining why.

Then measured it against a general view, where the answer is known (a cube in
general position shows 9 of 12 edges):

```
max slope x1.5      nine at 1.00,    three at <= 0.04    margin 0.96
low quantile x3     nine at >= 0.42, three at <= 0.04    margin 0.38
|d - z| <= 1% of z  nine at >= 0.83, three at <= 0.08    margin 0.75
```

The original was the best of the three by a distance. The 22% was **the
fixture**, and no test at any tolerance could have separated edges that land on
the same pixels. Reverted, kept the table in the comment, and the cube scene
now offsets every yaw by 0.35 rad so no shot is ever axis-aligned.

Third fixture in this repo to lie about something because nobody looked at it,
after the black-and-white square and the HDR background. It is starting to feel
less like bad luck.

### Recall was asked from the wrong side

First scoring run: segments 73% precision, 40% recall. The 40% bothered me
enough to draw an overlay, and one view had 88 misses out of 24 detections.

The ball. Its silhouette is a polyline of ~100 three-pixel facets, and the
pipeline draws one straight segment down the middle of a dozen of them. My
matcher credited, per detection, the single nearest ground-truth edge — so that
was one found and eleven missed. A pipeline doing exactly the right thing,
scored at 8%.

Precision walks the detections; recall walks the ground truth. They are not
each other's inverse and one pass cannot do both. 65% after, then 55% on the
bigger sweep.

Neither of these showed up in a table. Both were obvious in one picture. Wrote
`scripts/overlay.js` for it — ground truth in white/grey, detections in
green/red, corners as rings and dots — and it earned its place immediately.

### What 24 views say

12 positions × 2 lighting, 256px, 160 samples, denoised.

|  | detected | real | invented | missed | precision | recall |
|---|---|---|---|---|---|---|
| segments | 372 | 252 | 120 | 204 | 68% | 55% |
| corners | 661 | 162 | 499 | 36 | 25% | 82% |

25% precision is `corners` working as specified — hypotheses, not detections.
The question is whether the evidence sorts them:

```
endpointGap alone                            F1 0.80   precision 71%   recall 92%
sigma alone                                  F1 0.76   precision 73%   recall 78%
reach alone                                  F1 0.70
support alone                                F1 0.40
endpointGap <= 7 px AND sigma <= 0.2 px      F1 0.89   precision 94%   recall 84%
```

Three things the design doc had wrong, now corrected in §5.

**The 14× no-overlap separation was a property of that one image.** Real
corners run to 18 px of `endpointGap` at the 99th percentile; invented ones
start below 1 px. Best single threshold keeps 92% of the real at 71% precision.
Useful. Not clean.

**`sigma` is a discriminator**, and §5 said in as many words that it is not —
"says how well-located an answer is once you already believe it". The reasoning
was sound and the premise was wrong: yes, two long clean lines extended far
still intersect precisely, but *most invented corners are not from long clean
lines*. They are short fragments extrapolated a long way, which is exactly what
`sigma` is built to be sceptical of. On the cube's nine long segments it carried
nothing; across 24 views averaging fifteen segments each it nearly matches
`endpointGap`.

**`support` carries nothing.** §5 names it alongside `endpointGap`. F1 0.40, and
the best combination sits at `support >= 1`, which is every candidate.

The pair reaching **94% precision from two numbers already in the record** is
the result I would keep if I kept one. It also rescues the "expensive follow-up
may never be needed" argument, whose stated premise (endpointGap separates
perfectly) is now false.

### Things that bit

- **Backticks inside a template literal. Fourth time this session**, and I had
  read the note warning about it three hours earlier. `USAGE` in lab-cli.js.
- **An async test that passed for the wrong reason.** The suites here use
  `try { fn() } catch`, which sees a Promise come back, prints `ok`, and lets
  the rejection land as an unhandled rejection after the verdict. One case in
  `test/groundtruth.js` reads a file. Made the harness await, then broke the
  assertion deliberately to check it actually fails now.
- **`match` had to refuse mismatched dimensions.** Scoring a 512 run against
  256 truth produces numbers, not an error, and they look plausible — every
  distance roughly doubled.
- **pt-lab's denoiser is off by default** (`denoiseEnabled = false`). So every
  image this generator has ever produced carried the raw path-traced noise
  floor. Added `--denoise` rather than turning it on, because it would silently
  move every number already recorded — but it is worth knowing that the 08-26
  and 08-27 helmet counts were measured on noisy renders.
- **The cube sits exactly on the table** (both at y=0.75). Its bottom edges are
  coplanar with the surface, which is a genuinely awkward visibility case and
  the max-slope tolerance handles it — 1.00 on all four.

### Still open

- **The helmet, with this apparatus.** The user asked for cube-only and that
  was right for the corner question, but the 156-segment count from this
  morning still has no breakdown. Everything needed to get one now exists;
  it is one `--scene helmet --truth` run away.
- **The AOV passes are exported and nothing consumes them.** Depth, normal and
  albedo are written and the only thing reading any of them is pt-lab's own
  visibility test. Classifying an unmatched detection as texture / shading /
  noise needs a per-pixel comparison the lab has no operation for. That is the
  natural next slice, and it is what would explain the 120 unmatched segments —
  from the overlays, at least some are the cube's shadow.
- **Every threshold above is tuned to a cube in a lit room.** 24 views of one
  subject. A photograph will not behave like this.
- `corners` at ~125 s on 24,510 features, unchanged. Not a problem at ~15.
