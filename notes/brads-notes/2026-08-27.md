## Why it was headless, honestly

Two tools, two answers, and only one of them holds up.

`lab-cli.js` — genuine. It reads images and writes JSON; there is nothing to
look at. Its window exists **only** because `load` borrows Chromium's decoder,
which lives in a renderer. It also has to run under xvfb in CI.

`generate-cli.js` — symmetry with the runner, plus not wanting a window
stealing focus for minutes. No technical reason at all: `exportPNG` renders
offscreen at the requested size whether the window is visible or not, and the
generator was already excluded from CI, so the usual argument did not apply
either.

The cost was not the missing window. It was never looking.

## Watching it

`--show` on the CLI, and **Panes → Generate Images… (⌘G)** in the app: a
Generate frame with the parameters, a live progress log, and a "show the render
window" box that makes pt-lab's own window appear, path tracing in front of
you.

The constraint that shapes the frame, and will keep shaping it:

> The frame does **not** host the path tracer.

pt-lab is three.js plus an OIDN WASM blob behind a GPU renderer. Bundling it
into the app costs a few megabytes and costs CI an extra checkout, for
something the interface does not otherwise need — and `file:` dependencies must
resolve at *install* time even when nothing imports them, so it cannot simply
be added to package.json without breaking `npm ci` anywhere the sibling
checkout is absent.

So the main process runs it in its own window and sends progress over IPC. Two
small messages: options in, progress and file paths out. No pixels — renders go
to disk and come back through `load` like any other file.

That boundary is why growing the frame is cheap. Every pt-lab control (camera,
material, room kind, object transforms) is one more field in the frame and one
more key in the options object. Nothing about the boundary changes.

Shared orchestration lives in `src/generate/driver.js` — scheme, window,
download intercept, sweep — with the CLI as a wrapper that prints what the
frame displays. Same reasoning as `lab-cli.js` driving `window.lab` rather than
reaching for `Session`: two ways in is two things to drift.

## Things that bit

- **Backticks inside a template literal, third time this session.** `USAGE` in
  generate-cli.js is a template literal, and I wrote a backticked `--room none`
  into the help text. It fails as `SyntaxError: Invalid left-hand side expression in postfix
  operation` — pointing at a line that looks fine. Same shape as the two in
  test/renderer.js. Anything written *into* a template literal has to use
  quotes.
- **`app.quit()` ignores `process.exitCode`** and always exits 0. Looked like
  the fix for the Windows 0xC0000005 crash on exit; turned three passing tests
  into failures. The actual fix was noticing both crashing cases were *usage*
  paths that had no reason to start Electron at all — parse arguments at module
  scope and exit through `process.exit()` before `whenReady`.
- **`console-message`'s positional `level` is a number where 2 is a WARNING.**
  So `level >= 2` quietly promotes every warning to an error. That is how a
  CSP warning failed a generator run and printed itself as a blank line. The
  event object reports level as a string. `test/renderer.js` still uses the
  strict form deliberately — it is what caught the willReadFrequently warning.
