## Where the project is

The lab goes from a PNG to described geometry:

```
A  = load("cube.png", as=linear)
G  = gray(A)
B  = gaussian(G, sigma=1.4)
Gx = sobel(B, axis=x)
Gy = sobel(B, axis=y)
M  = sobel(B, axis=mag)
N  = nms(M, Gx, Gy)
S  = segments(N, Gx, Gy)
R  = merge(S)
F  = fit(R)
C  = corners(F)
```

Sixteen operations. 270 tests across nine suites, green on macOS, Linux and
Windows.

## Numbers from the cube, for reference

`assets/cube-1-256x256.png`, 256×256:

- 9 segments after `merge`, 42–63 px, worst residual 0.00–0.83
- angles cluster in three families — 0–16°, 77–85°, 139–157° — which is three
  visible faces
- 14 corner candidates, of which **4 have three agreeing segments** (a cube in
  general position has exactly four vertices where three visible edges meet)
  and 2 more have a reach of 1.1 and 1.4 px (the silhouette vertices)
- the other 8 reach 46–92 px and are spurious

`minMag=0.005`, not the original 0.02. The nms magnitude on this image peaks at
**0.0585** — an order of magnitude below a synthetic 0→1 step.

## Open questions

- Should `load` default to `as=linear` rather than `as=srgb`? Still open in
  `design-lab-model.md` §11.
- Does `pt-lab-workspace` write gamma-encoded or linear PNGs? Every image in
  `assets/` declares nothing, so the lab assumes sRGB by convention. If the
  renderer writes linear, that assumption is wrong and every `toLinear` applies
  a curve that was never there.
- Higher-precision input needs a native decoder — Chromium gives 8-bit RGBA.
  Worth doing only when an experiment actually needs the precision.
