## The styleText error is a Node version, not a broken dependency

Ran `npm run dev` in `paneless-workspace` on the system Node and got two errors
stacked, of which only the first is the truth:

```
You are using Node.js 18.17.1. Vite requires Node.js version 20.19+ or 22.12+.
...
file:///.../@sveltejs/vite-plugin-svelte/src/utils/log.js:4
import { styleText } from 'node:util';
SyntaxError: The requested module 'node:util' does not provide an export named 'styleText'
```

`styleText` arrived in Node 20.12/22. On 18 the import simply does not exist, so
a plugin deep in Vite's chain throws a SyntaxError about a named export. Read on
its own — which is how it will be read, because it is last and it has a stack —
it looks like a corrupt install or a bad dependency version. It is neither.

**Fix:**

```bash
nvm use          # reads the repo's .nvmrc
```

and if the shell has not loaded nvm at all — which is what being on 18.17.1
means, since that is the system Node and not something nvm selected:

```bash
source ~/.nvm/nvm.sh && nvm use
```

## The two repos pin different versions

| | `.nvmrc` |
|---|---|
| `cv-lab-2` | `22` |
| `paneless-workspace` | `24.11.0` |

Installed here: v20.20.2, v22.23.2, v24.11.0. So `nvm use` per directory
actually matters; they do not agree, and cd-ing between them without it leaves
whatever the last one selected.

They are compatible in the direction that matters: cv-lab-2 wants 22.12+ and
24.11.0 satisfies it. Claude ran cv-lab-2's whole suite on v24.11.0 all session
without trouble.

If the manual `nvm use` gets tiresome, nvm's zsh integration runs it on every
`cd` into a directory holding an `.nvmrc`:
https://github.com/nvm-sh/nvm#deeper-shell-integration

## Why cv-lab-2 does not fail this way and paneless does

`cv-lab-2` runs `scripts/check-node.js` ahead of install, build and test, and
CLAUDE.md records the reason in as many words: the requirement *used to* surface
as a styleText export error from inside Vite's plugin chain. So the guard exists
because this exact confusion already happened once, in this project.

`paneless-workspace` has the `.nvmrc` but no equivalent guard, so it still fails
the unhelpful way. Worth copying the guard across if it bites again — it is one
script and a `pre` hook.

# What the AOV passes said, once anything read them

`explain()` landed and the passes finally got consumed. Two findings, and the
second is the one I did not expect.

## Segments: the shading hypothesis holds, hard

Cluttered scene — cube on a table, ball beside it, area-lit room — six views,
203 detected segments, 123 of which matched no geometry. Classified:

```
shading    111   90%
occlusion   10    8%
crease       2    2%
```

Nine in ten "invented" segments were the detector correctly finding a shadow
boundary or a specular terminator. The overlay says the same thing at a glance:
the sphere is covered in red where its specular detail is, and there is a red
band under the cube exactly where the contact shadow falls.

So `(not geometry)` was never one finding. It was a detector that was wrong
pooled with a detector answering a question nobody asked it.

## Corners: it is mostly NOT the detector, and not shading either

311 invented corners:

```
shading    191   61%
occlusion  114   37%
crease       6    2%
```

37% sitting on real depth steps is a lot, so I checked what formed them rather
than guessing. Of those 114:

```
both segments matched real geometry   55
one matched, one not                  51
neither matched                        8
```

**Half of them are two real occluding contours crossing.** Where the sphere's
silhouette crosses the wall line, the image genuinely has a corner and the
geometry does not — there is no mesh vertex there, because nothing touches.
A T-junction.

Ground truth lists mesh vertices, so it counts every one of those as invented.
That is a **modelling limit, not a detector defect**, and it means corner
precision on a scene with more than one object is measuring something other
than what it claims. 13% precision reads like a broken detector; a good part of
it is the truth model being unable to represent the thing being found.

Two things I have NOT established: whether the truth *should* include image-space
T-junctions (they are view-dependent, so they are not a property of the scene the
way an edge is), and whether the remaining 51 mixed cases are the same
phenomenon or something else.

## Caveats on the numbers above

`maxDepth` varied 4.28–4.53 across the six images and I used 4.4 for all of
them. A ≤3% scale error against a 0.02 m threshold on ~1 m steps changes
nothing, but the run was not exact. Fixed afterwards — `explain` takes the
truth slot now and reads the real per-image value.

One scene, one detector configuration. The bare `cube-1` scene had almost no
invented detections to classify, which is why the cluttered one was needed and
also why the two are not directly comparable.

## The gap that made this awkward

`maxDepth` was parsed by `parseGroundTruth` all along and thrown away by the
`groundTruth` kernel, which destructured only `{ features, width, height }`. So
the one number needed to read a depth pass existed in the file, was read, and
could not be reached from inside the lab. Using `explain()` meant opening the
JSON and pasting the number into the script per image.

Worth remembering as a shape: a value that is parsed and dropped is harder to
notice missing than one that was never parsed, because the plumbing all looks
present.
